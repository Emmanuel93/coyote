# coyote v0.5.0 — reporte para el gate G5

Fecha: 2026-09-28 · Workstream: W-0005 · Autorizado a arrancar por: P-0004 (G4) · Estado: **propuesto para G5**

## Qué es esta versión

- **Cada PR se revisa contra todo el producto, no contra un repo.** El pipeline de cada repo del producto calcula el impacto del cambio en los otros repos y su riesgo por rutas. Un cambio R2 o R3 espera la aprobación de un dueño antes del merge: es la aprobación en equipo sin claves compartidas (D6, R17).
- **Los planes de un workstream se ejecutan.**
  - En `supervised`, el motor se detiene en cada paso para que la persona revise.
  - En `autonomous`, corre solo dentro de sus topes, en una rama `ws/`, con la aprobación del plan exacto.
  - El gate aplica igual en todos los modos.

## Qué se construyó

- **Pipeline de impacto** (ADR-0013 revisado, `docs/specs/ci-v1.md`).
  - `coyote install --ci github` genera el workflow de cada repo:
    - corre en `pull_request_target`, así el workflow y las reglas salen de la rama base;
    - usa acciones fijadas por commit y permisos mínimos;
    - toma las reglas de riesgo del proyecto (`risk:` en `project.yaml`).
    - `--check` verifica que los workflows estén al día.
  - `coyote gate pr`:
    - calcula el riesgo por rutas (R3: pipeline, CODEOWNERS, migraciones, auth, infraestructura; R2: contratos, dependencias, configuración) y por impacto (rompe a otro repo: R3; llega a otro repo: R2);
    - lee CODEOWNERS de la rama base, las revisiones del PR y quién escribió sus commits;
    - deja un solo comentario que se actualiza en cada push.
  - `coyote ci impact` queda como el reporte de impacto solo.
- **Motor de workstreams** (ADR-0014, `docs/specs/workstream-v1.md`). `coyote ws check|status|run|continue`:
  - `check` valida el contrato de cada paso (A2): agente, salida esperada, tope, entradas y secciones obligatorias.
  - `status` muestra el avance y el costo contra el tope del plan.
  - `continue` acepta lo que corrió; con `--redo "qué cambiar"` repite el paso con la revisión, y con `--retry` lo repite tal cual.
  - El estado sale del ledger: el equipo ve lo mismo después de un `pull`.
  - Si un paso deja acciones en la cola del gate, el motor se detiene; cuando la persona decide, retoma la sesión de Claude Code.
  - `autonomous` exige tres cosas:
    - la rama `ws/<W>`;
    - un tope de plan;
    - tu aprobación del plan exacto, atada a su hash, revisada antes de cada paso y evaluada por ti al final.
- **Gate.** Un agente no puede correr `coyote run`, `ws run` ni `ws continue`, ni detrás de envoltorios del shell. Leer `.git/config` del proyecto se bloquea como una credencial.
- **Cierre.** `coyote close` agrega la tabla de pasos del plan.

## Revisión adversarial

Un revisor independiente atacó el código nuevo en dos pasadas, con reproducciones.

**Primera pasada: 13 hallazgos, todos corregidos con prueba.**

- **Alto.** `gate pr` bajaba a R1 un PR que tocaba workflows o migraciones si traía un `.gitattributes` con `-diff`, un archivo vacío o un nombre con comillas.
- **Alto.** Un PR desde un fork pasaba el chequeo: GitHub cuenta un job saltado como éxito.
- **Alto.** Con `pull_request`, el PR controlaba el workflow que lo evalúa. Ahora es `pull_request_target`: el código del PR se lee como dato y nunca se ejecuta.
- **Medio.**
  - Un agente podía lanzar `coyote ws continue` detrás de `script`, `bash -c` o `eval`.
  - Ctrl-C dejaba a Claude Code corriendo sin registro.
  - Si el ledger fallaba, el motor repetía el paso.
  - Un dueño por correo en CODEOWNERS dejaba aprobar a cualquiera.
- **Bajo.**
  - Carrera en el lock.
  - Revocar no detenía un loop autónomo.
  - `run --ws` ignoraba el tope del plan.
  - `.GIT` en macOS.
  - Carpetas con espacios.
  - Pedidos de cambios no verificables.
  - Además: una aceptación ya no vale para otro artefacto, y quien escribió commits del PR no aprueba.

**Segunda pasada: los 13 cerrados.** Encontró 1 medio y 4 bajos más:

- el bloqueo dependía de una lista de envoltorios (`watch`, `parallel`, `find -exec`, variables). Ahora el gate busca la palabra `coyote` seguida del subcomando, sin lista;
- Ctrl-\ no se capturaba;
- las rutas del PR podían armar enlaces en el comentario;
- un PR de más de 250 commits;
- mensajes de commit bloqueados de más.

Todos corregidos, salvo uno que queda a propósito: con dueños que no se pueden verificar, un pedido de cambios de cualquiera detiene el merge.

## Límites conocidos

- **Evaluación de forks.** Con `pull_request_target`, el job de un fork tiene los secretos de lectura. El código del fork nunca se compila ni se ejecuta, y leerlo usa git sin filtros, hooks ni transportes. Aun así, es superficie nueva: el workflow y los tokens son de solo lectura.
- **Reevaluar después de aprobar.** `pull_request_target` no corre con las revisiones: después de aprobar, se vuelve a correr el chequeo o se empuja un commit.
- **Cambios al workflow.** Para que cambiar el workflow también pase por un dueño, hace falta activar en GitHub "Require review from Code Owners", y los tres repos todavía no tienen CODEOWNERS.
- **Scripts escritos por un agente.** El gate lee el texto de un comando, no lo que un script hace por dentro. Un script que escribió un agente y que se aprueba a ciegas puede llamar a coyote. `coyote review` muestra su contenido.
- **Sin Claude Code real.** `--resume` con `--agent` en headless no se probó contra Claude Code real; si falla, `--retry` corre el paso de nuevo.
- **T37, corridas medidas.** Están pendientes: las lanzas tú. Hasta tenerlas, el motor no tiene números reales de costo por paso.
- **Tokens para el pipeline.** Hoy coyote y los tres repos son de tu cuenta: un solo token fino de solo lectura (`COYOTE_PRODUCT_TOKEN`) cubre los cuatro. Si los repos pasan a una organización, un token fino cubre un solo dueño y se agrega `COYOTE_TOOL_TOKEN` para leer coyote (D26).
- **Exigir el chequeo.** Para que un chequeo requerido bloquee el merge en un repo privado, GitHub pide un plan de pago (protección de ramas o rulesets). Sin él, `fail` marca el chequeo en rojo pero no bloquea.
- **Fuera de este release.** La visibilidad de costos por persona (D10) y el hub de la organización (D12) no se construyeron: pasan a v0.6.
