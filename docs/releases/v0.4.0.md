# coyote v0.4.0 — reporte para el gate G4

Fecha: 2026-09-28 · Workstream: W-0004 · Autorizado a arrancar por: P-0003 (G3) · Estado: **aprobado en G4** (`coyote/approvals/P-0004.json`)

## Qué es esta versión

Un cambio se ve contra todo el producto, no contra un repo. Coyote lee los repos de un producto (servicios con sus BFF, app móvil, backoffice web) sin tocarlos y saca del código qué expone y qué consume cada módulo. Con eso dice, para un endpoint, un tópico o un diff, a quién afecta y por qué, directo o a través de un BFF, y qué se rompe. Además, `coyote run` corre agentes con Claude Code con el gate activo, topes de turnos y de dólares y el costo en el ledger. El router baja de modelo cuando el presupuesto aprieta.

## Qué se construyó

- **Producto multi-repo** (ADR-0011, `docs/specs/product-v1.md`).
  - Un proyecto `type: product` registra sus repos por ruta local.
  - `coyote map` arma el mapa de interfaces:
    - Spring: anotaciones, WebClient, RestClient, RestTemplate, Feign y Kafka;
    - Dart: Dio y `http`;
    - TypeScript: `fetch`, `axios` y `request`.
  - Cada interfaz cita `repo@sha:archivo#L`. `map --check` sirve para la CI y `--ambiguous` muestra los empates.
- **Impacto.**
  - `coyote impact` acepta un endpoint, un tópico, un texto o el diff de uno o varios repos a la vez.
  - Reporta qué cambia, quién lo usa directo y quién a través de un BFF. En este último caso sigue las llamadas entre métodos hasta tres saltos.
  - En un diff compara el contrato de cada archivo antes y después: lo eliminado marca a sus consumidores como **se rompe**.
  - Salida en texto, Markdown para un PR o JSON.
- **Propuestas por repo.** `coyote extract` propone `README.coyote.md` y `CONTEXT.coyote.md` de cada repo con:
  - propósito y comandos;
  - módulos;
  - de qué otros repos depende y quién usa cada módulo.

  Respetan los topes de CCF-doc y nunca pisan lo que edita una persona.
- **Contexto para agentes.** El índice incluye el mapa y las propuestas. `ask` y `get context` responden quién llama qué, y la caché de otro repo queda en el proyecto que pregunta.
- **`coyote run`** (ADR-0012, `docs/specs/run-v1.md`). Corre Claude Code headless:
  - pasa el agente, el modelo del router y los topes;
  - usa `--permission-mode dontAsk` y solo herramientas de lectura;
  - la entrada lleva la tarea, el paquete de contexto y el impacto.

  Guarda el artefacto en el workstream y registra un evento `run` con tokens, modelo y costo estimado. No corre sin el gate instalado ni dentro de una sesión de agente, y el gate bloquea `coyote run` desde un agente.
- **Router v1.**
  - Modelo por agente y piso por riesgo (R2 sonnet, R3 opus).
  - Al 80 % del presupuesto mensual baja un nivel, salvo R3; al 100 % no corre.
  - El tope de cada corrida nunca pasa de lo que queda del mes.
  - `coyote router` muestra la decisión para cada agente.
- **`coyote close`.** Llena la sección de consumo de `close.md` desde el ledger, por modelo y por agente, sin tocar lo que escribió la persona.

## Revisión adversarial

Un revisor independiente atacó el código nuevo con reproducciones. Encontró 8 problemas, todos corregidos con prueba antes de este reporte:

1. **Alto.** Leer un repo podía ejecutar programas que el repo configura:
   - los filtros `clean` de git durante `status` o `diff-index`;
   - `uploadpack` en un clon parcial, que además escribía objetos en `.git`.

   Ahora los filtros se anulan por nombre y ningún transporte está permitido.
2. **Alto.** Las escrituras usaban un temporal de nombre fijo. Un symlink plantado con ese nombre desviaba la escritura fuera del proyecto. Ahora todo se escribe con un temporal de nombre al azar, creado en exclusiva. El arreglo cubre el mapa, la caché del índice, el ritmo y la cola del gate.
3. **Medio.** Una barra vertical en una ruta de archivo rompía el formato del mapa y, con él, `map`, `impact` y `extract`.
4. **Medio.** `warn_at` o `stop_at` como NaN desactivaban el rechazo al 100 %. `--max-usd NaN` pasaba.
5. **Medio.** Una salida de Claude Code en forma de lista se registraba como falla con costo cero.
6. **Bajo.** `get context <ruta>` escribía la caché en el otro proyecto.
7. **Bajo.** Envoltorios como `env -u CLAUDECODE`, `nice`, `timeout` o `sh -c`, y las comillas, bajaban el bloqueo de `coyote run` a "pide aprobación".
8. **Bajo.** Una corrida rechazada por falta de gate no quedaba en el ledger.

## Incidente en el piloto

Antes de la prueba de solo lectura, dos lecturas pasaron por comandos que refrescan el índice de git:

- el análisis de tu trabajo sin commit en fintech-services usó `git diff`;
- yo corrí un `git status` en los tres repos.

Ese refresco reescribe los datos de estado de `.git/index`, lo mismo que hace `git status` en tu terminal: no cambia archivos, commits ni ramas. Desde el arreglo, coyote usa comandos de plomería que nunca escriben. Verifiqué que el índice de fintech-services queda idéntico antes y después de un análisis.

## Límites conocidos

- Los extractores leen patrones, no compilan. Quedan sin enlace, y marcados, los clientes generados, las rutas armadas en tiempo de ejecución y los tópicos elegidos por un mapa de configuración.
- Un DTO que cambia marca los endpoints cuyo método lo menciona; decidir si el cambio es de contrato sigue siendo de la persona.
- `coyote run` no corrió contra Claude Code real: aquí no hay una sesión tuya. Los argumentos y el formato de salida se verificaron con la documentación de Claude Code. La primera corrida real es parte de lo que autoriza G4.
- El costo es la estimación de Claude Code, no la factura. Sin tabla de precios en `router.yaml`, el costo no se separa en entrada y salida.
- `supervised` y `autonomous` siguen en v0.5: primero hay que medir corridas reales.
- El consumo de esta construcción no se midió con coyote: se construyó fuera de `coyote run`.
