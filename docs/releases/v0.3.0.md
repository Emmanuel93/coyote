# coyote v0.3.0 — reporte para el gate G3

Fecha: 2026-09-28 · Workstream: W-0003 · Autorizado a arrancar por: P-0002 (G2) · Estado: **esperando autorización**

## Qué es esta versión

El gate humano deja de ser una promesa. En Claude Code y en Cursor, todo lo que un agente haga con efectos espera a que apruebes esa acción exacta. Leer, buscar y pedir contexto siguen libres. Un agente no puede aprobarse, desarmar el gate ni leer tus credenciales. Además hay 14 agentes y 8 skills que se instalan con un comando, y el ledger registra qué agente actuó según lo reporta el IDE, no según lo que declara el comando.

## Qué se construyó

- **Gate por hash** (ADR-0009, `docs/specs/gate-v1.md`). `coyote gate check` es el hook previo de Claude Code y Cursor; también lee el formato de Codex y Copilot. Decide en este orden:
  1. atribución a IA (R15);
  2. bloqueos que ninguna aprobación levanta;
  3. lectura libre;
  4. el hash de la acción exacta.

  Falla cerrado ante errores y cuando falta coyote.
- **Cola de aprobaciones.**
  - `coyote approvals` muestra la cola y `coyote review` el comando o el diff exacto, con quién lo pidió.
  - `coyote approve` acepta `--uses`, `--for`, `--all` y `--bash`; `reject` y `revoke` piden motivo.
  - Cada aprobación queda firmada con una clave local y vale en esa máquina y esa copia del proyecto, por 24 horas como máximo.
  - Los usos y las revocaciones van en el ledger.
  - Aprobar exige una terminal interactiva fuera de una sesión de agente.
- **14 agentes y 8 skills `coyote-*`** (ADR-0010, `docs/specs/install-v1.md`). Cada agente declara modelo, turnos, herramientas de lectura, skills y entregable. El proyecto puede agregar los suyos en `coyote/agents/` y `coyote/skills/`.
- **`coyote install --ide claude-code|cursor|all`.** Fusiona tu configuración sin pisarla, apaga la atribución y instala el hook, los agentes, las skills y `AGENTS.md`. `--check` sirve para CI. `coyote doctor --ide` prueba el gate con decisiones simuladas.
- **Identidad.**
  - `--agent` solo acepta agentes conocidos.
  - Lo que registra una sesión de agente queda a nombre del IDE.
  - Un subagente no puede declararse otro.
  - `push` desde un agente no publica en `main`.
- **Autonomía.** `supervised` y `autonomous` se aceptan en `project.yaml`, pero hasta v0.4 el gate aplica `manual`. `status` y `doctor` lo dicen.

## Revisión adversarial

Un revisor independiente atacó el gate con reproducciones. El analizador de shell resistió unos 45 intentos de evasión. Encontró 4 problemas y 4 notas menores, todos corregidos con prueba:

1. **Alto.** Con un `coyote/project.yaml` inválido, el gate dejaba pasar las lecturas, incluidas las de credenciales. Ahora un proyecto ilegible bloquea todo, y `project.yaml` (donde vive la autonomía) quedó protegido.
2. **Alto.** `git config --list` pasaba como lectura y podía mostrar tokens de la configuración de git. Ahora solo pasa `--get` de claves sin secretos. `git remote` solo muestra nombres, porque las URLs pueden llevar tokens.
3. **Medio.** `go vet` pasaba como lectura, pero compila C del repo (cgo). Ahora necesita aprobación, igual que `go env` completo.
4. **Medio.** `review` imprimía el comando tal cual: con escapes de terminal, un agente podía mostrarte un comando distinto del que aprobabas. Ahora los caracteres de control e invisibles se muestran escapados, y el ledger no los guarda.
5. **Notas menores:**
   - El hash de Bash incluye ahora todo campo con valor (`run_in_background`, `dangerouslyDisableSandbox`).
   - Las aprobaciones se atan a la copia del proyecto.
   - Se documentaron el reconocimiento de MCP de lectura por nombre y el `--agent` que no se puede verificar en IDEs que no reportan el subagente.

Antes de la revisión se cerraron tres vías más: `rg --hostname-bin`, `jq env` y `diff -r` sobre carpetas con credenciales.

## Hallazgo del entorno de construcción: firmas en los commits

Los commits desde v0.1.0 hasta `df2e320` llevan una firma SSH hecha con una llave del entorno donde se construye coyote, no con la tuya. La configuración global de git de ese entorno firma cada commit. La firma no nombra a ninguna herramienta, pero GitHub mostrará esos commits como no verificados. Las etiquetas no están firmadas. Desde `6a37ca8`, la configuración local del repo desactiva la firma y los commits nuevos van sin ella. Reescribir los commits anteriores cambiaría todos los SHA, las etiquetas y las referencias de las aprobaciones y del ledger, y requeriría que hicieras un push forzado. Es una decisión de G3.

## Límites conocidos

- El gate se probó con las entradas documentadas de Claude Code y Cursor, no con los IDEs corriendo: aquí no se pueden abrir. `coyote doctor --ide` lo verifica en tu Mac. El formato exacto del Write de Cursor no está documentado; si trae campos desconocidos, se hashea completo.
- WebFetch y WebSearch se tratan como lectura: la salida de datos del proyecto por red la controlan los permisos de dominio del IDE. Un `.env` del proyecto se lee libremente.
- Lo que hace un comando aprobado es responsabilidad de quien lo aprueba.
- `supervised` y `autonomous`, el router, `coyote run` y el cierre con costo llegan en v0.4. Windsurf, Copilot, Codex, Gemini CLI, Junie, Zed y Devin, en v0.5.
- `coyote init` sigue creando solo el gate de atribución de v0.1. El gate humano se activa con `coyote install`.
- El consumo de esta construcción no se midió: coyote todavía no se conecta con el proveedor de modelos.

2. Activar el gate en tu Mac con `coyote install --ide claude-code`, en coyote y en los proyectos que elijas, y probarlo con `coyote doctor --ide claude-code`.
3. El piloto en seco sobre un dominio real, en solo lectura, con tu revisión de cada artefacto.
4. Confirmar los supuestos D6, D11, D19, D20, D21 y D22.
5. Decidir qué hacer con las firmas del entorno en los commits anteriores.
6. Arrancar v0.4: router de modelos, `coyote run`, modos `supervised` y `autonomous`, cierre con costo y web v1.
